# Decision log

This file holds the full reasoning behind the "Key design decisions" table at the top of each notebook. Each notebook has a section with one row per decision:

- **Decision:** the choice that was made.
- **Rationale:** the question the choice answers, why it wins, and the alternatives rejected. Each cell opens with the step number and title that the notebooks refer to (for example "Step 2 above").
- **Evidence:** what was measured or found in the data.

"Section N" means a numbered section of that notebook.

# p02_ingest_notices

| Decision | Rationale | Evidence |
|---|---|---|
| Split the work into partitions that each hold fewer than 100,000 notices. | **Step 1: Plain offset paging cannot reach most of the data.** Can we page through all 423k notices with `rows` and `os` (offset)? No: a simple loop would silently stop at about a quarter of the notices. | The API sits on Azure Cognitive Search, and an offset above 100,000 fails with "Value must be between 0 and 100000 ($skip)". Pages are also capped at 1,000 rows. |
| One partition per project country (facet filter `project_ctry_name_exact`), the only filter the API honours. The 2018 cutoff is applied by ordering instead (Step 3), and a completeness check against the total guards the gaps a facet split can leave (Step 5). | **Step 2: How to partition.** Which filter splits the data reliably? We wanted a date filter, because only notices from 2018 are needed. Rejected: *date windows* (the preferred design): split adaptively, halving any window that returns more than 100,000, and reconcile the windows' sum with the total. Not possible here, because the API ignores date filters. Rejected: *id ranges or `id % n`*: also even and complete, but the API offers no range or modulo filter on `id`; splitting after download does not help, because the full set cannot be downloaded in the first place. | The date parameters (`strdate`/`enddate`, `fq=noticedate:[...]`, `noticedate_exact`) are ignored or rejected. The facet filter `project_ctry_name_exact` works: 184 values whose counts add up **exactly** to the total, the largest being India with 47,452. |
| Sort by `id` newest first, and stop a country when a whole page is older than 2018-01-01. | **Step 3: A stable order, and the 2018 cutoff.** How do we page without skipping or repeating notices, and stop at 2018? The `id` order is unique and follows time. Newest-first also tolerates notices published *during* the run: a new notice pushes everything down by one, which repeats a row (removed by the `MERGE` key) but never skips one. Rejected: the default order by notice date. | The default order is by notice date, which has many ties, so the same offset can return different rows on two calls. Sorting by `id` is unique, and ids are issued in time order (`OP00000005` is from September 2005; about 50k ids predate mid-2018). |
| 500 rows per page, 4 countries in parallel, retries with exponential backoff. Every page is saved as a file, so a restart skips finished pages and finished countries. | **Step 4: Page size and politeness.** How big should a page be? 500-row pages are consistently fast. Rejected: 1,000-row pages, whose time varied widely. | 1,000 rows with `notice_text` took 17 s once and 3 s another time; 500 rows consistently took about 2 s (about 2 MB). |
| Measure the gap (total minus facet counts) and read the unfiltered feed newest-first until that many country-less notices are saved, instead of asserting that the gap is zero. | **Step 5: Notices without a country.** Do the country partitions still cover everything on a later run? No: notices published without a project country fall outside every facet. | On the first run the facet counts added up exactly to the total; on a re-run about 20 hours later 200 notices were missing from every facet. They were recent notices published without a project country (184 of the newest 1,000 had none; the last of the 200 was found about 37,500 notices deep). The completeness assert caught it. |

| Decision | Rationale | Evidence |

It is the value repeated, so summing the raw column would double-count every joint venture. | In 7,083 of the 8,864 multi-supplier contracts every row carries the identical amount. In the other 1,781 the two values differ by a fixed ratio, almost always exactly 1.0303 or 1.0003: a conversion artefact, not a split. Example: contract 1543858 lists AIRES INGEGNERIA and ALL INGEGNERIA, both at US$161,538.89. |
| `contracts` holds project, method, category, dates and reference once; `contract_suppliers` keeps only what varies by member. | **Step 2: Contract attributes really are contract-level.** Can project, method, category, dates and reference move from the row level to one row per contract without losing information? Yes, because each has a single value per contract. | For all 282,890 contracts each of these columns has exactly one value (re-checked in the quality table at the end of the notebook). |
| One crosswalk (`proc_intel.countries`) maps every code and name to ISO alpha-2, or to the Bank's regional code. | **Step 3: Country codes do not line up.** Does the awards feed's country code join to the governance indicators? No. Without the crosswalk, five borrowers would silently lose their governance indicators. | The feed uses the Bank's own codes. The notices feed only has names, with its own spellings ("Turkey", "Türkiye", "Vietnam", "Somalia"). |

The one award row without an id gets a surrogate id `NOID-<hash>`, so the bridge keeps its key. | **Step 4: Who is a supplier?** Is `supplier_id` an identity? No: it is a registration id, and one firm can hold several. | Individual consultants are anonymised: supplier "INDIVIDUAL CONSULTANT" with a 16-character hashed id (65,121 rows). Some notices also carry beneficial-ownership tables naming private persons. |

Nothing at write time, so the counts are the actual guarantee. | Unity Catalog keys are informational. Nothing stops a duplicate or an orphan from being written. |

# p04_supplier_resolution

| Decision | Rationale | Evidence |
|---|---|---|
| A shared id links two names only if they are similar (cosine >= 0.5) or one is the other's acronym. Otherwise the id is split and follows its most used name. The splits are counted in the notebook. | **Step 1: How reliable is `supplier_id`?** Can we trust "same id = same firm", and "different id = different firm"? The second is false and the first is only mostly true, so a shared id needs a name check. Rejected: trusting every shared id (the first run), which chained different firms into one entity. | The second is false: 6,648 names appear under more than one id. The first is *mostly* true: of the ids that carry several names (awards plus award notices), about 97% are spelling variants. The dissimilar rest are partly acronyms or translations of one firm ("SAHE" = "SOCIETE AFRICAINE D'HYDRAULIQUE ET D'ELECTRICITE"), partly two parties under one id ("SANJEEV KUMAR" / "SUSHIL KUMAR"). The first run trusted every shared id: ENTREPRISE SATU-SA (Niger) shared ids with eight partner firms, which chained nine firms (BAANA, EGAM, ENISAB, ...) into one entity of 77 records. |
| Cosine of TF-IDF weighted character trigrams, compared only within the same supplier country (blocking). Jaro-Winkler and token-set ratio are kept as explanatory columns only. | **Step 2: Choosing the similarity score.** Token-set ratio, Jaro-Winkler, or TF-IDF character n-grams? Trigrams tolerate typos and spacing, cosine ignores word order, and TF-IDF down-weights words every supplier uses. Blocking by country keeps the work small and matches how firms register. Rejected: Jaro-Winkler, which rewards a shared prefix, and token-set ratio, which rewards containment (see Evidence). | The variants are typos ("PRICEWTERHOUSECOOPERS"), spacing ("ABCCONSULT"), word order and extra words ("(DWP GROUP)"). Jaro-Winkler rewards a shared prefix, so every "CONSTRUCTION ..." pair scores high. Token-set ratio scores 1.0 whenever one name is contained in the other, so "AGRITCHAD" would match "GROUPEMENT SETI AGRITCHAD". Blocking takes minutes for 370k records on one node, and "PWC ALBANIA" and "PRICEWATERHOUSECOOPERS" (Poland) are different legal entities. |
| A fuzzy link must also agree on the **distinctive words**: the words that are rare among that country's supplier names ("LAO CAI" vs "THAI BINH" do not agree). | **Step 3: The first threshold produced giant clusters.** With a plain cosine threshold, what do the clusters look like? Chains of near-neighbours joined different firms. Rejected: a plain cosine threshold. | At 0.6 the largest cluster had 2,540 records, at 0.7 still 433. Vietnamese names that share a long generic phrase ("CONG TY CO PHAN XAY DUNG VA THUONG MAI ..." = construction and trade joint-stock company) and 12 provincial "LAND REGISTRATION OFFICE OF &lt;province&gt; PROVINCE"s became one entity. In the first prototype (award names only) the distinctive-word check raised precision on the labelled pairs from 0.73 to 1.00 at the same threshold and shrank the largest cluster from 433 records to a real firm. |
| A personal-looking name whose every word also appears in more than 3 *other* names of that country (names without its remaining words: ARUN SHARMA, RAJ KUMAR, ...) gets **no name links**; rare personal names may still match exactly. Fuzzy links need the distinctive words to match at 0.9. | **Step 4: Personal names.** Can two records named "ARUN KUMAR" be merged? No, a common personal name is not an identity, but a rare one can be. Rejected: counting all names that contain the word (the first version), which made a firm's own spelling variants look common; counting only names without the other words fixed that. The 0.9 bar keeps one-letter differences such as "KARANJEET" / "CHARANJEET" apart. | One third of the records look like personal names (small works and supplies, many in India and Ethiopia). "AJAY KUMAR" alone appears under 24 ids; the labelled "ARUN KUMAR" pair are contractors in two different forest divisions. But "UASSI MWEMA" (Comoros) is the same contractor in two contracts of one project. Under the first version "SEC DIARRA", an audit firm with 40 ids, was kept apart. |
| Threshold 0.70 (the sweep in section 4 shows the trade-off). Because these labels also chose the threshold, the random link audit in section 7 is the less biased precision estimate. | **Step 5: Measuring it.** How good is the result, in numbers? Labels drawn from every similarity band test hard and easy cases alike, and p15 replaces the agent reference labels with three-tier labels for the final figures. | 100 labelled pairs, drawn from every similarity band (0.3 to 1.0) so that hard and easy cases are both present, plus a random audit of 40 produced fuzzy links; both label sets were made by an AI agent during the build (agent reference labels). Results are in sections 4 and 7. p15 relabels the same 100 pairs with the project's three-tier escalation (code checks, a panel of three LLM judges, an AI adjudicator that records evidence) and reports the final figures: precision 1.00 (95% CI 0.90-1.00) and recall 0.90 (0.77-0.96) on 97 decided pairs. |
| One extra word on the longer side is allowed, "(LEAD)" markers are dropped, and singular/plural forms share their generic status. | **Step 5 (continued): the strict word match was too strict.** The measurement showed that the distinctive-word rule rejected true variants. | The strict word match rejected true variants that add one word ("ECONOMIC CONSULTING ASSOCIATES LIMITED (ECA)", "PRICEWATERHOUSECOOPERS ... (PWC INDIA)", "... (LEAD)") or differ in singular/plural of a common word ("OMNI SOLUTION TECHNOLOGIE" vs "OMNI SOLUTIONS TECHNOLOGIES"). |

# p05_link_notices_awards

| Decision | Rationale | Evidence |
|---|---|---|
| Keep both tiers (exact project + reference, and the STEP activity id). Links where the notice comes after signing are stored but flagged, and never used for durations. | **Step 1: How far does the exact reference go?** What share of contracts can be matched to a tender notice by reference alone? A notice published after signing is a reference re-used for a later round, not the tender of this contract. | Exact project + reference matches found tender notices for about 61,500 contracts; the STEP activity id added only about 2,300 more (most STEP references are copied unchanged). About 6,000 links had the notice published **after** the contract was signed. |
| Replace the ratio with an exact structural rule: the references must be equal after deleting one block of 1-3 **letters** (never digits) from the longer one. It also catches different packages one character apart. | Use descriptions only for contracts **without** a STEP id, require >= 0.8 similarity and a clear margin over the second-best notice, and measure the tier separately in the tender-link audit (section 5). | **Step 3: Description matching needs a guard.** For contracts with no matching reference, does the description find the tender? It is the only bridge when the contract reference is the borrower's own number, but it confuses near-identical packages of one project. | Even at similarity >= 0.9, descriptions matched the wrong package where one project tenders near-identical packages ("Civil Work Package (CWP) 7" vs "CWP 8", "Fish Landing in Brgy. Among one-to-one pairs whose notice names an awardee, the share confirmed is the automatic precision check for reference matching. | **Step 4: Award notices share references across lots.** Can award notices be linked the same way? Not by reference alone, because one reference covers all lots and call-offs of a tender. | By reference alone, award notices and contracts formed about 980,000 pairs (section 3 shows the counts): one reference is shared by all lots and call-offs of a tender (one reference appears on 188 contracts). |
| Coverage is reported per competition level. The timeline model in phase 2 should be trained on openly competed contracts, where the notice is the norm. | **Step 5: What can be timed?** Which contracts should have a tender notice at all? Most contracts are never advertised, so overall coverage would understate the linking. | Most contracts are never publicly advertised: Request for Quotations, direct selection and individual consultants make up about 80% of contracts. |

# p07_tender_risk_model

| Decision | Rationale | Evidence |
|---|---|---|
| Model notices from 2019-07-01 to 730 days before the snapshot, with the duration capped at 730 days. Newer notices are scored, not trained on, and the survival view in section 9 handles them as censored. | **Step 1: Which tenders can be used at all?** Is the duration of every timed contract a fair training example? No: the edge cohorts are biased. Within the chosen window every duration up to the cap is observable. Rejected: a plain "test on the newest year" split, which would report that tenders became twice as fast. | The awards feed holds contracts signed from 2019-07-01 to the snapshot, so the median notice -> signing time by notice year is 465 days for 2018 (only slow tenders reached the feed), 154-189 days for 2019-2024, 135 for 2025 and 95 for 2026 (only fast tenders are signed yet). 1.5% of durations exceed 730 days. |
| The risk target is **slow**: duration above the P75 of the same method x category in the training years. Re-advertisement rates are reported, not modelled. | **Step 2: What does "re-bidding risk" mean in this data?** Can re-advertisement be the risk target? No: it is rare, and a re-tender under a new reference is invisible. Rejected: re-advertisement as the target. | 1.3% of training contracts (1.5% of test) have more than one tender notice linked, and only 135 of 81,600 (project, reference) pairs of tender notices repeat exactly; only 10 IFB notices carry a "Revised" status. Base rate of slow: 25.0% in training, 22.4% in the test notices (newer tenders are faster). |
| Contract amount, review type and the outcome-model risk score are left out. Governance indicators are taken for the year before the notice, and market history for the 36 months before the notice month. | **Step 3: Which inputs are known on the notice date?** Which candidate features would leak the outcome? All three excluded features are unknown on the notice date or reveal the future. | The contract amount is only known at award and no pre-award estimate exists; review type is not on the notice, so open notices could not be scored with it; the outcome-model risk score exists only for projects still active in 2026, so its presence reveals the project's future. |
| Calibrate the interval with conformalised quantile regression on the last training half-year. The model is registered as `@champion`. | **Step 4: Does the model beat the lookup table?** Is a model better than the peer-group quantiles an analyst would look up? Yes, but its raw interval under-covers, and calibration fixes the coverage while keeping it narrower than the peer table. | The model wins on all four rolling-origin folds (pinball loss of the median 38.1-42.1 vs 44.5-49.2 for the peer table) and on the test notices: MAE 76 vs 88 days, mean pinball 24.6 vs 29.1. But the raw P10-P90 interval covered only 68% of test outcomes (target 80%): 16% fell below P10 and 15% above P90. Calibration moves the lower bound down by 0.136 and the upper bound up by 0.112 log-days (about 13% and 12% in days). Test coverage is then 80.7% (9.8% below, 9.5% above), with the interval still 12% narrower than the peer table's. |
| Publish the probability with the threshold it refers to; recalibrating on recent data is the first maintenance task. | **Step 5: Is the slow-tender score useful, and is it calibrated?** Does the classifier rank tenders better than the peer group's historical slow rate? It ranks clearly better, but its probabilities drift with the base rate. | ROC-AUC 0.747 vs 0.584, PR-AUC 0.494 vs 0.295 (base rate 0.224). The predicted probabilities run slightly high in the lower deciles, consistent with the lower base rate of the test notices. |
| Use Kaplan-Meier (KM) to compare timing across groups and cohorts, not to estimate how many tenders fail. Use the Weibull AFT for readable time ratios. | **Step 6: Can "not signed yet" be told apart from "never signed"?** Can unsigned notices be treated as censored in a survival model? For young notices, yes; for old notices, no, because cancellations and link failures look the same. | For young notices the KM share signed within 180 days is 0.30-0.38 for every notice year 2019-2025, while the naive median of the observed durations falls to 144 days (2025) and 91 (2026). For old notices the curves flatten at 0.56-0.67, the share of notices p05 manages to link. KM medians among linked notices: consulting 319 days, works 132, goods 127, non-consulting 125. Weibull AFT time ratios: Request for Bids 0.42x the time of the other open methods (which are mostly consultant selections); Latin America 1.28x vs Europe and Central Asia; +1.2% per advertising day. Its test concordance (0.694) is below LightGBM's (0.721). |

# p08_procurement_agent

| Decision | Rationale | Evidence |
|---|---|---|

Unit tests cover each of these cases. | **Step 2: Which completion-report passages are lessons about procurement?** Can headings and keywords pick the procurement-relevant passages out of 100-page reports?
